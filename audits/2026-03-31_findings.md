# Audit Findings

Дата аудита: 2026-03-31

## Scope

Аудит выполнен по текущему состоянию рабочей копии проекта `fast-dump`.
Проверялись:

- архитектура модулей `cli`, `app`, `network`, `sender`, `receiver`
- wire protocol и transport layer
- sender/receiver session flow, resume model и frame commit semantics
- тестовое покрытие и базовые quality gates

Команды, использованные как автоматические сигналы:

```text
cargo test
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
```

Итог этих прогонов:

- `cargo test`: проходит
- `cargo fmt --check`: не проходит
- `cargo clippy --all-targets --all-features -- -D warnings`: не проходит

## Findings

### Medium: проект не проходит собственный strict static-analysis gate

`cargo clippy --all-targets --all-features -- -D warnings` сейчас падает минимум по двум причинам:

- `clippy::too_many_arguments` на `prepare_frame_build` в `src/sender/frame.rs:309`
- `clippy::items_after_test_module` в `src/receiver/shared.rs:10`

Это не runtime regression, но это уже operational defect:

- любой CI, который считает `clippy -D warnings` обязательным, будет красным
- в текущем виде нельзя утверждать, что кодовая база поддерживает строгую hygiene-политику

Затронутые места:

- `src/sender/frame.rs:309`
- `src/receiver/shared.rs:10`

Рекомендация:

- либо привести `clippy` к зелёному состоянию
- либо явно зафиксировать набор разрешённых lint suppression, если это сознательный выбор

### Medium: `src/network/protocol.md` отстаёт от фактической реализации

Документ `src/network/protocol.md` противоречит реальному состоянию проекта.
На момент аудита в нём написано:

- что в live runtime используется только начальный handshake (`src/network/protocol.md:10-16`)
- что dump/resume session loop ещё не подключён (`src/network/protocol.md:16`)
- что `transport` использует только `Hello / HelloAck / Error` (`src/network/protocol.md:110-111`)
- что `dump_id` в handshake пока отправляется пустой строкой (`src/network/protocol.md:112`)
- что journal, resume loop, frame commit и dump pipeline ещё не подключены (`src/network/protocol.md:113`)

Это уже не соответствует реальности:

- `sender` и `receiver` реально используют `ResumeQuery`, `ResumeState`, `FrameStart`, `FrameChunk`, `FrameEnd`, `Ack`, `Finish`, `FinishAck`
- resume и frame commit проверяются и unit-, и integration-тестами

Риск здесь не академический:

- новый разработчик будет принимать неверные решения по интеграции
- внешние потребители документации получат неправильное описание протокола

Рекомендация:

- синхронизировать `src/network/protocol.md` с текущим wire behavior
- отдельно пометить, какие части являются contract, а какие implementation notes

### Medium: в production state machine остались `expect`-паники на внутренних инвариантах

В коде sender есть места, где нарушение внутреннего инварианта ведёт к panic вместо контролируемой ошибки:

- `src/sender/session.rs:273`
- `src/sender/session.rs:309`
- `src/sender/source.rs:281`

Сейчас эти паники прикрыты текущей логикой, и тесты их не задевают.
Но это всё ещё плохая failure mode для production pipeline:

- process abort сложнее диагностировать на реальном окружении
- при следующем рефакторинге можно случайно превратить edge case в аварийное завершение процесса

Рекомендация:

- заменить эти `expect` на `anyhow::bail!` или эквивалентный `Result`-путь
- оставить комментарий, какой именно инвариант считается нарушенным

### Low: рабочее дерево не `rustfmt`-clean

`cargo fmt --check` падает на нескольких изменённых файлах, в том числе:

- `src/receiver/listener.rs`
- `src/sender/frame.rs`
- `src/sender/mod.rs`
- `src/sender/readers.rs`
- `src/sender/session.rs`
- `src/sender/source.rs`

Это не влияет на корректность, но означает:

- форматирование не стабилизировано
- любые последующие PR будут шумнее
- review signal-to-noise хуже, чем должен быть

Рекомендация:

- прогнать `cargo fmt`
- добавить форматирование в локальный pre-commit или CI

### Low: в normal dependencies висит неиспользуемый `jwalk`

`jwalk` объявлен в `Cargo.toml:11`, но по коду `src`, `tests` и `benches` использование не найдено.

Это создаёт лишний долг:

- дополнительная зависимость в lockfile
- лишняя поверхность для security/compatibility updates
- лишний шум при чтении dependency graph

Рекомендация:

- удалить `jwalk` из `Cargo.toml` и `Cargo.lock`, если нет скрытого плана вернуть его в ближайшем изменении

## Positive Notes

Несмотря на перечисленные замечания, текущее состояние проекта в целом сильное:

- `cargo test` проходит полностью
- архитектура sender после рефакторинга стала существенно лучше по memory scaling
- receiver-side journal и frame commit semantics выглядят аккуратно отделёнными
- integration-тесты покрывают push/pull, resume, frame rollback и корректность итогового архива

## Residual Risks

- самый тяжёлый soak/scaling сценарий остаётся `#[ignore]` в `tests/connectivity/stress.rs:8`
- кодовая база пока не защищена зелёным `fmt + clippy` барьером
- протокольная документация сейчас ненадёжна как источник истины

## Recommended Next Steps

1. Сделать зелёными `cargo fmt --check` и `cargo clippy --all-targets --all-features -- -D warnings`.
2. Обновить `src/network/protocol.md` под реальный runtime contract.
3. Убрать `expect` из production state machine sender.
4. Удалить `jwalk`, если он действительно больше не нужен.
5. Добавить отдельный длительный stress/perf pipeline, чтобы большой сценарий запускался регулярно, а не только вручную.

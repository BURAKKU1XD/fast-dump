# Overview Audit

Дата аудита: 2026-03-31

## Summary

Проект в целом находится в хорошем состоянии по архитектуре и по функциональной корректности текущего v1 pipeline.
На момент аудита:

- `cargo test` проходит полностью
- sender/receiver роли разведены достаточно чисто
- frame-based resume model реализована и покрыта тестами
- итоговый receiver artifact остаётся валидным `.tar.zst`

Главные проблемы на момент обзора не в core logic, а в инженерной гигиене и сопровождении.

## Findings

### Medium: strict static-analysis gate не зелёный

`cargo clippy --all-targets --all-features -- -D warnings` падает.
Минимум на двух местах:

- `src/sender/frame.rs:309`
- `src/receiver/shared.rs:10`

Это не runtime-баг, но это уже дефект процесса сопровождения.

### Medium: protocol markdown устарел

`src/network/protocol.md` описывает состояние, где dump/resume loop ещё не подключён.
Это уже не соответствует текущей реализации и integration-тестам.

Риск:

- документация больше не является надёжным источником истины

### Medium: в production path остались panic-based инварианты

В sender есть `expect`, которые при нарушении внутреннего инварианта приводят к panic вместо контролируемой ошибки:

- `src/sender/session.rs:273`
- `src/sender/session.rs:309`
- `src/sender/source.rs:281`

Сейчас это не ломает тесты, но это хрупкая failure mode для реального runtime.

### Low: repo не rustfmt-clean

`cargo fmt --check` падает на ряде файлов, связанных в основном с последними изменениями sender/receiver.

### Low: неиспользуемая dependency

`jwalk` объявлен в `Cargo.toml`, но в коде проекта на момент аудита не используется.

## Current State

### Что выглядит хорошо

- модульная структура проекта уже цельная: `app`, `cli`, `network`, `sender`, `receiver`
- sender после рефакторинга действительно ушёл от полного file map и полного compressed frame buffer
- receiver-side journal, frame commit и finalize path выглядят логично и хорошо тестируются
- integration tests покрывают push/pull, resume, rollback unacked frame и корректность итогового архива

### Что выглядит слабее

- quality gates не доведены до зелёного состояния
- документация отстаёт от кода
- тяжёлый stress path запускается только вручную

## Residual Risks

- `tests/connectivity/stress.rs` остаётся `#[ignore]`, значит самый тяжёлый сценарий не входит в регулярный прогон
- при следующих рефакторингах panic-based инварианты в sender могут превратиться в реальные аварийные завершения процесса
- рассинхрон между `protocol.md` и кодом может привести к ошибочным изменениям в будущем

## Recommended Next Steps

1. Починить `cargo fmt --check`.
2. Починить `cargo clippy --all-targets --all-features -- -D warnings`.
3. Синхронизировать `src/network/protocol.md` с реальным runtime contract.
4. Убрать `expect` из production state machine sender.
5. Удалить `jwalk`, если он больше не нужен.
